# 功能规格：发布文件的校验和与构建证明

**特性分支**: `017-release-verification` | **创建日期**: 2026-11-15 | **状态**: 已批准
**输入**: macOS 版没有 Apple 签名与公证（规格 015 的决定），首次打开要手动放行；Windows 版同样未签名。正式签名需要付费的开发者账号，暂不做。先用免费的方式，让下载者能确认安装文件完整、确实来自本仓库的构建，再决定是否放行。

## 用户场景与测试

### 用户故事 1 —— 核对下载的文件没有损坏或被改动 (P1)

下载者在打开安装文件之前，用系统自带的命令核对它和发布者公布的一致。

**独立测试**：从 Releases 下载任一安装文件与对应的校验文件，按 README 中的命令核对。

**验收场景**
1. **当** 打开某个版本的 Release 页面，**那么** 每个安装文件旁边都有一个同名的 `.sha256` 校验文件。
2. **假设** 在 macOS 上下载了安装文件和校验文件，**当** 按 README 在终端执行核对命令，**那么** 显示该文件“OK”。
3. **假设** 在 Windows 上下载了安装文件和校验文件，**当** 按 README 在 PowerShell 中执行核对命令，**那么** 显示一致。
4. **假设** 文件被改动了哪怕一个字节，**当** 核对，**那么** 核对失败。

### 用户故事 2 —— 确认文件来自本仓库的构建 (P1)

下载者确认安装文件是本仓库的持续集成从某次公开提交构建出来的，而不是别人上传的。

**独立测试**：对任一安装文件执行 README 中的构建证明核对命令。

**验收场景**
1. **当** 对某个版本的任一安装文件执行核对命令，**那么** 结果显示它由本仓库的发布流程构建，并给出对应的提交。
2. **假设** 是从别处得到的同名文件，内容与发布的不同，**当** 核对，**那么** 核对失败。
3. **当** 在仓库的 Attestations 页面查看，**那么** 能看到每个版本安装文件的构建证明。

### 用户故事 3 —— 在文档中找到方法 (P1)

**验收场景**
1. **当** 阅读 README（中文、英文）的安装部分，**那么** 能找到上述两种核对方法，以及何时应当核对（首次放行未签名的程序之前）。
2. **当** 在内置使用指南中查找，**那么** 能找到同样的方法。

### 边界情况

- 校验文件与安装文件在同一个 Release 页面：它能发现下载损坏、镜像或转发途中被替换，不能防止 Release 页面本身被篡改；后者由构建证明覆盖。文档如实说明两者的区别。
- 本规格不改变“未签名、首次打开需要放行”的现状，文档中的放行步骤保留。

## 需求

### 功能需求

- **FR-1701** 每次发布时，每个安装文件（Windows 安装版、免安装版、macOS `.dmg`）都必须附带一个 SHA-256 校验文件，与安装文件同时上传到同一个 Release。
- **FR-1702** 每次发布时，每个安装文件都必须生成 GitHub 构建证明，记录它由本仓库发布流程从哪次提交构建。
- **FR-1703** README、README.en 与使用指南必须说明两种核对方法（macOS、Windows 各自的命令）。

### 非功能需求

- **NFR-1701** 免费：只使用公开仓库可免费使用的 GitHub 功能；不新增项目依赖。
- **NFR-1702** 安装文件本身、体积与安装方式不变（宪章 VII）。

## 成功标准

- **SC-1701** 下一个版本发布后，按文档对三个安装文件分别执行两种核对，全部通过。

## 澄清与假设

- Apple 签名与公证、Windows 代码签名需付费，不在本规格范围；以后另开规格。
- 核对构建证明需要 GitHub CLI（`gh`）；不想安装的用户可在仓库的 Attestations 页面查看。
